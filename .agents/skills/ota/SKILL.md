# OTA в ebbflow-lamp

Полная документация — `docs/ota.md` в корне репозитория. Здесь — выжимка
для работы с кодом.

## Архитектура одним абзацем

Устройство раз в `CONFIG_LAMP_OTA_CHECK_INTERVAL_MIN` (дефолт 60 мин)
дёргает `api.github.com/repos/<CONFIG_LAMP_OTA_REPO>/releases/latest`,
сравнивает `tag_name` со своей версией (semver) и при появлении новой
скачивает ассет `ebbflow-lamp-<чип>.bin` через `esp_https_ota` в свободный
OTA-слот и перезагружается. Код — `main/ota_update.c` (~200 строк,
самодостаточный модуль, точка входа `ota_update_start()` из `app_main`).

## Железные правила (нарушение = OTA молча ломается)

1. **Буферы HTTP 2048** в конфиге esp_https_ota — после 302-редиректа
   GitHub отдаёт подписанный URL ~900+ байт, дефолтных 512 не хватает.
2. **TLS только через `esp_crt_bundle_attach`** — GitHub меняет CA,
   захардкоженный сертификат сломается.
3. **Репозиторий публичный** — анонимный API, 60 запросов/час на IP.
   Токенов в прошивке нет и не надо.
4. **Версия живёт в корневом CMakeLists** (`project(... VERSION x.y.z)`),
   CI переопределяет тегом через `-DPROJECT_VER`. Не разводить второй
   источник версий.
5. **Разметка — своя `partitions.csv`** (2 слота по 0x1E0000, без factory).
   Смена разметки = erase-flash устройства.
6. Самотест rollback (`esp_ota_mark_app_valid_cancel_rollback` в `main.c`
   после Wi-Fi+SNTP) нельзя удалять — без него загрузчик откатит любую
   OTA-прошивку.

## Отладка на устройстве

- Логи: тег `ota` (+ `esp_https_ota`). Ключевые строки: «есть новая версия»,
  «скачиваю обновление», «Writing to <ota_N>», «версия актуальна».
- `idf.py monitor` требует TTY. Из автоматики порт читается pyserial
  (115200), ресет — импульс RTS при DTR=False (иначе плата уходит в
  download mode и молчит).
- Таблица «симптом → причина → лечение» — в `docs/ota.md`, раздел
  «Диагностика».

## E2E-проверка после изменений OTA-кода

1. Прошить кабелем сборку с версией ниже релизной и
   `CONFIG_LAMP_OTA_CHECK_INTERVAL_MIN=1` в sdkconfig.
2. Выпустить релиз (скилл `firmware-release`).
3. Дождаться в логе перехода на новую версию. Без этой проверки
   изменения в `ota_update.c` не считаются готовыми.
