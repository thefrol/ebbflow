# Идеи на будущее

Наброски архитектуры. Веб-интерфейс v2 уже реализован (см. ниже), остальное
— планы. Порядок — от простого к сложному; дальше v2 идти необязательно.

## v2: локальный веб-интерфейс

**Реализовано (веб-часть).** `esp_http_server` на порту 80:

- страничка `main/web/index.html` встроена в прошивку через `EMBED_FILES`
  (без SPIFFS), vanilla JS + fetch;
- `GET/POST /api/settings` — on/off в "HH:MM" (строки на границе API,
  внутри минуты от полуночи), gpio, enabled; частичные поля допустимы,
  валидация с 400 + текстом причины;
- `GET /api/info` — имя, версия прошивки, чип (задел под сканер флота);
- POST → `settings_save()` + `lamp_apply_settings()` — расписание меняется
  на лету без перезагрузки.

### Открыто в v2: заменить post-build inline-assets.js на vite-plugin-singlefile

Сейчас фронтенд собирается Vite, но по умолчанию Vite выдаёт `index.html` плюс
отдельные ассеты (`assets/index.js`, `assets/index.css`). Чтобы встроить всё в
прошивку одним файлом, используется костыль `web/scripts/inline-assets.js`:
он после `vite build` парсит HTML, читает CSS/JS, вставляет их в `<style>` и
`<script type="module">` вручную, экранирует `</script>` и удаляет папку
`assets`.

Это ломко и не нужно: есть штатный плагин `vite-plugin-singlefile`, который
делает inline внутри пайплайна Vite. План:

1. Установить `vite-plugin-singlefile` в `web/`.
2. Заменить `plugins: [vue()]` на `plugins: [vue(), vitePluginSinglefile()]`.
3. Убрать `rollupOptions.output.entryFileNames/chunkFileNames/assetFileNames`,
   `cssCodeSplit` и прочие настройки, которые были нужны только для
   `inline-assets.js` (хэши больше не важны, плагин сам всё свернёт).
4. Удалить `web/scripts/inline-assets.js` и вызов `node scripts/inline-assets.js`
   из `tools/build-web.sh` (или вообще заменить `build-web.sh` на
   `npm run build` внутри `web/`).
5. Убедиться, что `web/dist/index.html` остаётся одним самодостаточным
   gzip-файлом, который `EMBED_FILES` в прошивку встраивает как раньше.
6. Проверить на устройстве: `GET /` отдаёт `text/html` + gzip, веб-интерфейс
   открывается, кнопки работают.

Это уберёт ручной парсинг HTML и сделает сборку frontend чище.

## Идентификация и обнаружение устройств в LAN

Вынесено в отдельную готовую спеку: **`ideas/mdns-discovery.md`** —
mDNS-анонс `_ebbflow._tcp` с TXT-визиткой, hostname `<имя>.local`,
эндпоинт `/api/peers` и блок «Другие лампы» в вебе.

Запасной вариант остаётся: скрипт-сканер на компьютере
(**реализовано (v0.5.0): `tools/scan.sh`** — обходит /24, дёргает
`/api/info`, фильтрует ответы по полям name/version/chip). Работает и там,
где роутер фильтрует multicast.

## Резервные сети и аварийная точка доступа

Сейчас Wi-Fi один, зашит в конфиге, при обрыве — бесконечный реконнект.
Дальше:

- **Несколько известных сетей** (домашняя + hotspot телефона и т.п.):
  список {SSID, пароль} в NVS, при недоступности текущей — сканирование
  (`esp_wifi_scan_start`) и подключение к лучшей по приоритету/RSSI,
  round-robin при неудачах. Нативного «списка сетей» в ESP-IDF нет,
  это своя логика в `wifi_setup`.
- **Свой AP при полном провале**: если ни одна сеть не отвечает N минут
  (или кредов нет вовсе) — устройство поднимает точку доступа
  `ebbflow-lamp-setup` с captive-порталом: форма ввода SSID/пароля,
  сохранение в NVS, перезагрузка в STA-режим. Это же решает первичную
  настройку нового устройства без перепрошивки. Альтернатива —
  `esp_wifi_provisioning` (provisioning через BLE с телефона).
- Учитывать: C3/C6 видят только 2.4 ГГц — 5 ГГц-сети в список добавлять
  бессмысленно.

## v3: флот и внешний контроллер (опционально)

Если ламп станет много и захочется централизованного управления:

- **MQTT**: брокер где-то в сети (или в облаке), топики
  `ebbflow/<id>/settings`, `ebbflow/<id>/state`, `ebbflow/<id>/status` (LWT).
  Устройства подписываются на свой `<id>`, контроллер шлёт расписания.
- Контроллер — отдельный маленький сервис (сайт/бот), ему MQTT и нужен.
- Плюс: единая точка правды, расписания переживают перепрошивки.
- Минус: заметно сложнее. Локальный веб (v2) закрывает большинство сценариев
  для 1–3 устройств, поэтому сначала он.

## OTA — обновление по воздуху

**Реализовано (v0.3.0).** Устройство опрашивает GitHub Releases репозитория
и обновляется само, источник бинарей — CI:

- релиз = пуш тега `v*` → GitHub Actions собирает прошивку под обе цели
  в контейнере `espressif/idf:v6.0.2` (Wi-Fi креды — из Secrets) и публикует
  релиз с ассетами `ebbflow-lamp-esp32c3.bin` / `-esp32c6.bin`;
- устройство раз в `CONFIG_LAMP_OTA_CHECK_INTERVAL_MIN` дёргает
  `releases/latest`, сравнивает `tag_name` со своей версией (semver,
  версия прошивки = `project(VERSION)`/`-DPROJECT_VER` из тега) и качает
  ассет под свой чип через `esp_https_ota`;
- TLS — `esp_crt_bundle_attach` (покрывает и github.com, и CDN ассетов);
- буферы HTTP 2048: подписанный URL после 302-редиректа длиной ~900+ байт
  не влезает в дефолтные 512 (на этом же споткнулся ESPHome, issue #13786);
- анонимный rate limit GitHub API — 60 запросов/час на IP, поэтому интервал
  по умолчанию 60 минут;
- откат при неудачной загрузке: `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`,
  прошивка подтверждает себя в `app_main` после Wi-Fi + SNTP
  (`esp_ota_mark_app_valid_cancel_rollback`), иначе загрузчик вернёт
  предыдущий слот.

Опционально дальше: anti-rollback + Secure Boot V2 (усложняет производство,
eFuse необратимы), ETag/If-None-Match для экономии rate limit, ручной
триггер проверки из будущего веб-интерфейса.
