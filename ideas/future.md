# Идеи на будущее

Наброски архитектуры. Пока ничего из этого не реализовано — v1 просто гоняет
расписание из NVS. Порядок — от простого к сложному; дальше v2 идти необязательно.

## v2: локальный веб-интерфейс (следующий шаг)

Каждое устройство само хостит маленькую страничку:

- `esp_http_server`, пара REST-эндпоинтов: `GET/POST /api/settings`
  (on/off/enabled/gpio), дальше `settings_save()` + `lamp_apply_settings()`.
- Статика странички — через `EMBED_FILES` компонента, без SPIFFS.
- Зачем: менять расписание без перепрошивки с телефона в той же Wi-Fi сети.

## Идентификация и обнаружение устройств в LAN

Уже сейчас hostname = `CONFIG_LAMP_DEVICE_NAME` (в NVS в будущем). Дальше:

- **mDNS** (`mdns_init`): `ebbflow-lamp-1.local`, сервис `_ebbflow._tcp` —
  устройства находятся `dns-sd`/`avahi-browse` без сканирования сети.
- Запасной вариант — скрипт-сканер на компьютере: обойти подсеть, дернуть
  `/api/info` (имя, MAC, версия прошивки) у всех, кто отвечает.
- Уникальный ID устройства: MAC (`esp_read_mac`) + заданное имя; MAC —
  естественный первичный ключ для флота.

## Резервные сети и аварийная точка доступа

Сейчас Wi-Fi один, зашит в конфиге, при обрыве — бесконечный реконнект.
Дальше:

- **Несколько известных сетей** (домашняя + hotspot телефона и т.п.):
  список {SSID, пароль} в NVS, при недоступности текущей — сканирование
  (`esp_wifi_scan_start`) и подключение к лучшей по приоритету/RSSI,
  round-robin при неудачах. Нативного «списка сетей» в ESP-IDF нет,
  это своя логика в `wifi_setup`.
- **Свой AP при полном провале**: если ни одна сеть не отвечает N минут
  (или кредов нет вовсе) — устройство поднимает точку доступа
  `ebbflow-lamp-setup` с captive-порталом: форма ввода SSID/пароля,
  сохранение в NVS, перезагрузка в STA-режим. Это же решает первичную
  настройку нового устройства без перепрошивки. Альтернатива —
  `esp_wifi_provisioning` (provisioning через BLE с телефона).
- Учитывать: C3/C6 видят только 2.4 ГГц — 5 ГГц-сети в список добавлять
  бессмысленно.

## v3: флот и внешний контроллер (опционально)

Если ламп станет много и захочется централизованного управления:

- **MQTT**: брокер где-то в сети (или в облаке), топики
  `ebbflow/<id>/settings`, `ebbflow/<id>/state`, `ebbflow/<id>/status` (LWT).
  Устройства подписываются на свой `<id>`, контроллер шлёт расписания.
- Контроллер — отдельный маленький сервис (сайт/бот), ему MQTT и нужен.
- Плюс: единая точка правды, расписания переживают перепрошивки.
- Минус: заметно сложнее. Локальный веб (v2) закрывает большинство сценариев
  для 1–3 устройств, поэтому сначала он.

## OTA — обновление по воздуху

Уже заложено в прошивку с v1: разметка флеша с двумя OTA-слотами
(`CONFIG_PARTITION_TABLE_TWO_OTA=y` в `sdkconfig.defaults`), менять её на
устройстве в поле было бы болью, поэтому делаем сразу.

Что осталось для рабочего OTA (когда появится источник обновлений):

- компонент `esp_https_ota`: устройство забирает новый `.bin` по HTTPS в
  свободный слот (`ota_0`/`ota_1`), переключает загрузку на него;
- **источник бинаря — GitHub Releases** (решили использовать его):
  - CI (GitHub Actions): на тег `v*` собирает прошивку под обе цели
    (контейнер `espressif/idf:v6.0.2`) и кладёт `ebbflow-lamp-esp32c3.bin` /
    `ebbflow-lamp-esp32c6.bin` в релиз;
  - устройство опрашивает `api.github.com/repos/<owner>/ebbflow-lamp/releases/latest`,
    сравнивает `tag_name` со своей версией, скачивает ассет под свой чип;
  - URL ассета редиректит на `objects.githubusercontent.com` — `esp_http_client`
    ходит за редиректами сам (проверить `max_redirection_count` при настройке);
  - TLS: сертификаты GitHub покрывает `esp_crt_bundle_attach` (mbedTLS bundle),
    вшивать свой сертификат не нужно;
  - репозиторий приватный → в запрос нужен токен (захардкоженный токен в
    прошивке = повод задуматься, паблик-репо проще);
- версионирование: `project(... VERSION x.y.z)` или git-тег — устройство
  сравнивает версии и обновляется только на более новую;
- триггер: эндпоинт в будущем веб-интерфейсе («проверить обновление») или
  сообщение по MQTT;
- опционально откат: `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` — новая
  прошивка помечается valid только после самопроверки, иначе загрузчик
  возвращает предыдущую. Включать, когда OTA заработает.
